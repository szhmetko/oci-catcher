# oci-capacity-catcher

Ловилка свободной ёмкости Oracle Cloud Always Free, работающая на GitHub Actions.

В перегруженных регионах ёмкость освобождается на секунды, когда кто-то другой
гасит инстанс. Поймать это окно кликами в консоли практически невозможно, а
скрипт на домашней машине ловит только пока эта машина включена. Здесь ловля
идёт в CI и не зависит от локального железа.

## Как это работает

Один job живёт почти 6 часов — это потолок GitHub для одного запуска.
Расписание перезапускает его четыре раза в сутки. Поэтому известная
неточность планировщика Actions (задержки 5–30 минут в час пик) стоит
минут покрытия, а не часов.

Внутри прогона скрипт по кругу перебирает формы:

Каждый круг:

1. `VM.Standard.E2.1.Micro` — фиксированная, 1 GB RAM.
2. `VM.Standard.A1.Flex` 1 OCPU / 1 GB — минимально возможный ARM-след
   (у A1 минимум памяти 1 GB на OCPU).
3. `VM.Standard.A1.Flex` 1 OCPU / 6 GB — половина квоты.

Раз в `RARE_EVERY` кругов дополнительно: `VM.Standard.A1.Flex` 2 OCPU / 12 GB.

Порядок — от мелкого следа к крупному: планировщику OCI проще найти дырку под
маленький инстанс, чем под непрерывный блок. Поймав A1 любого размера, ты уже
знаешь, что ARM-ёмкость на хосте есть, и расширение через Edit Shape — отдельная
попытка с лучшими шансами, чем запуск с нуля.

Полная квота вынесена в редкие круги не из-за формы, а из-за бюджета вызовов.
Измерено: Oracle пропускает примерно три `LaunchInstance` за десятиминутное окно,
всё сверх этого получает 429. Это и есть реальный дефицит. Непрерывный блок на
2 OCPU / 12 GB — самая маловероятная из форм, и отдавать ей четверть каждого
круга значит недопробовать те три, которые действительно могут упасть.

По той же причине формы перебираются последовательно, а не параллельно. Вызов
к Oracle идёт около 110 секунд — он всё это время перебирает хосты, то есть одна
попытка покрывает почти двухминутный отрезок времени, а не мгновение. При
фиксированном бюджете вызовов последовательный перебор покрывает втрое больше
времени, чем залп, а ёмкость освобождается в случайный момент.

OCID образов и подсети резолвятся на старте прогона, в конфиге их держать не надо.
Фильтр по `--shape` сам выбирает нужную архитектуру: aarch64 для A1, x86_64 для micro.

Скрипт завершается сам, как только инстанс создан, и при старте проверяет через
API, нет ли уже живого инстанса — чтобы не ловить второй поверх первого и не
жечь квоту.

## Настройка

Репозиторий должен быть **публичным**: только там минуты Actions не лимитированы.
В приватном дают 2000 минут в месяц — этого хватит примерно на 4% покрытия.

Заведи в OCI отдельного пользователя под ловилку, а не используй свой админский
ключ. Достаточно такой политики:

```
Allow group catcher-group to inspect all-resources in tenancy
Allow group catcher-group to manage instance-family in tenancy
Allow group catcher-group to use subnets in tenancy
Allow group catcher-group to use vnics in tenancy
Allow group catcher-group to use network-security-groups in tenancy
Allow group catcher-group to read instance-images in tenancy
```

Тогда утечка ключа стоит максимум лишнего инстанса, а не всей тенанси.

### Secrets

Settings → Secrets and variables → Actions.

| Secret | Что это |
|---|---|
| `OCI_TENANCY_OCID` | OCID тенанси |
| `OCI_COMPARTMENT_ID` | Compartment для инстанса, обычно тот же root |
| `OCI_USER_OCID` | OCID сервисного пользователя |
| `OCI_FINGERPRINT` | Fingerprint его API-ключа |
| `OCI_REGION` | Home region, например `eu-madrid-1` |
| `OCI_SUBNET_ID` | Публичная подсеть. Если пусто — берётся первая найденная |
| `OCI_PRIVATE_KEY` | Приватный ключ целиком, вместе со строками BEGIN/END |
| `SSH_PUBKEY` | Публичный SSH-ключ, который ляжет в инстанс |
| `TG_TOKEN`, `TG_CHAT_ID` | Уведомления в Telegram, необязательно |

### Запуск

Actions → oci-capacity-catcher → Run workflow.

Шаг **Verify access** выводит список availability domains — если таблица
появилась, доступ настроен верно. Дальше шаг **Catch** печатает, сколько форм
попало в очередь.

## Настройки через переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DEADLINE_MIN` | 340 | Длительность прогона, меньше лимита GitHub в 360 |
| `ATTEMPT_GAP` | 35 | Пауза между попытками внутри круга |
| `ROUND_GAP_MIN` / `ROUND_GAP_MAX` | 40 / 80 | Джиттер между кругами |
| `BOOT_GB` | 50 | Размер загрузочного тома |
| `RARE_EVERY` | 5 | Раз во сколько кругов пробовать A1 2 OCPU / 12 GB |
| `UBUNTU_VERSION` | 24.04 | Версия образа, с откатом на 22.04 |
| `INSTANCE_NAME` | freqtrade | Display name будущего инстанса |

Про rate limit: Oracle отдаёт 429, если дёргать LaunchInstance слишком часто.
Штраф здесь нарастающий — первый карантин минута, каждый следующий подряд
плюс минута до десяти, и уровень спадает обратно, как только API снова
отвечает нормально. Фиксированная длинная пауза обходится заметно дороже.

## Известное ограничение

В публичных репозиториях GitHub отключает расписания после 60 дней без
активности в репозитории, молча и без уведомления. Если ловля затянется,
достаточно любого коммита раз в пару месяцев.
